# Agent evaluation methods: evidence and design inputs

The primary evidence supports evaluating memory strategies on paired, stateful workflows with separate outcome, trajectory, feasibility, grader, and cost records. [τ-bench](https://arxiv.org/html/2406.12045v1), [LongMemEval](https://arxiv.org/html/2410.10813v2), and [LoCoMo-Plus](https://aclanthology.org/2026.acl-long.1150.pdf) cover complementary parts of this problem. No cited source validates persistent records, conversation compaction, and full history head to head on ongoing synthetic business workflows. The transfer points are design guidance; the study results remain specific to their published tasks, agents, and graders.

## Evidence matrix

This matrix separates results demonstrated by each source from the design lesson inferred for this benchmark.

| [τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](https://arxiv.org/html/2406.12045v1), 2024, §§3–5 | It evaluates simulated user-agent conversations against both a unique final database state and required response information. ## Prioritized considerations

The following considerations preserve the benchmark’s existing outcome dimensions and add controls around comparison quality.

1. **Keep a paired scenario comparison.** Every memory arm must receive the same initial world, task intent, tool affordances, model, prompt, and user behavior. Reset or clone world state before each arm. Pairing controls task-mix variation; it does not control the model’s run variation ([τ-bench](https://arxiv.org/html/2406.12045v1), [τ²-Bench](https://arxiv.org/html/2506.07982v1)).
2. **Retain separate score dimensions.** Keep atomic facts, downstream work, obligations, critical violations, operational validity, and cost visible on their own. A final state can be correct after an unauthorized action; a conversation can show useful progress while its final result fails. Add a trajectory excerpt or first consequential error for failures that need diagnosis ([τ-bench](https://arxiv.org/html/2406.12045v1), [WebArena-Lite trajectory audit](https://arxiv.org/html/2610.01491v1)).
3. **Separate semantic quality from capacity feasibility.** Report whether an arm fits the context and tool budgets, finishes within its declared limits, and produces a valid run. Score semantic outcomes on valid trials and show coverage and all launched attempts alongside that score. Context overflow caused by a strategy belongs to that strategy’s feasibility result; provider outages and broken fixtures belong to infrastructure validity ([Inspect scoring policy](https://inspect.aisi.org.uk/scoring-policy.html)).
4. **Treat one rollout as a point observation.** Show task counts and paired task-level results. Do not infer reliability from one trajectory per arm. If ranking or stability matters, repeat a representative subset and report the observed interval or dispersion. Set the amount of repetition from pilot variance, decision precision, and cost; published counts from unrelated tasks are not defaults ([τ-bench](https://arxiv.org/html/2406.12045v1), [Blackwell et al.](https://arxiv.org/html/2410.03492v2)).
5. **Make scenario truth inspectable and agent-inaccessible.** Store initial state, expected final state, required actions, obligations, and critical rules as user-owned scenario material. Keep oracle values out of agent-visible prompts and context. Version the scenario and grader, and retain a digest with each run. A held-out scenario set is useful when model or package changes can overfit the visible suite; its size and custody are an owner decision ([τ-bench](https://arxiv.org/html/2406.12045v1), [Harbor verifier documentation](https://github.com/harbor-framework/harbor/blob/main/docs/content/docs/tasks/index.mdx)).
6. **Calibrate semantic grading.** Use deterministic state and trace predicates for facts and actions whenever possible. For open-ended responses, test the rubric against human labels, randomize blind pairwise order, retain the judge’s output, and expose judge failures rather than silently removing them from the denominator ([MT-Bench](https://arxiv.org/abs/2306.05685), [Inspect scoring policy](https://inspect.aisi.org.uk/scoring-policy.html)).
7. **Make cost and latency attributable.** Record agent, simulator, and grader tokens or charges separately, plus elapsed time, retries, tool calls, and hard budget stops. Report cost per trial and cost per successful task. A memory arm that fails to fit or costs more can still be compared honestly when feasibility and semantic quality remain separate ([τ²-Bench](https://arxiv.org/html/2506.07982v1), [Inspect evaluation logs](https://inspect.aisi.org.uk/eval-logs.html)).
8. **Offer two invocation paths without a hosted dependency.** A fast path can run scenario, schema, reset, oracle, and grader checks locally without model calls. A deliberate path can run named models and arms with explicit repeat counts, time, token, and spend caps. Retain immutable raw traces and run configuration so grading or analysis can be repeated offline ([Inspect scoring workflow](https://inspect.aisi.org.uk/scoring-workflow.html), [OpenAI agent workflow evaluation](https://developers.openai.com/api/docs/guides/agent-evals)).
9. **Validate simulated users as benchmark components.** Before comparing arms, check that the user script or simulator follows its instruction, respects its allowed tools, and does not make the task impossible. Record a simulator failure separately from an agent failure. If a model simulates the user, include its cost and configuration in the run record ([τ²-Bench](https://arxiv.org/html/2506.07982v1)).

## Minimal conceptual vocabulary

These terms are candidate concepts for later collision checking, not a naming decision.

- **Scenario:** One user-owned workflow definition, including initial state, conversational context, expected results, obligations, and grader inputs.
- **Arm:** One strategy configuration under comparison, such as full history, compaction, persistent records, or a control.
- **Trial:** One isolated execution of one arm against one scenario.
- **Run:** The declared set of trials and pinned model, harness, prompt, tool, budget, and grader versions.
- **Artifact:** The saved run manifest, trace, state changes, score breakdown, cost, and failure classification.

## Preserve, change, avoid, and defer

- **Preserve:** Existing separate measures for facts, downstream work, obligations, critical violations, operational validity, and cost; scenario ownership; raw run evidence.
- **Change:** Add paired scenario resets, explicit grading coverage, independent status for agent/task/grader/infrastructure failures, and a repeated subset for estimating trajectory variation when needed.
- **Avoid:** A single blended score as the only result, pass@k as a substitute for reliable execution, open-ended LLM scoring of checkable state, and conclusions about consistency from one run.
- **Defer:** A universal evaluation platform, external scenario hosting, broad benchmark imports, and final package vocabulary until the repository unit resolves naming collisions and integration needs.

## Unanswered questions

- Does the target workflow expose state through an API, a browser, or both? This determines whether UI fidelity is part of the claim.
- Will each scenario use a deterministic user script, a seeded simulator, or a paid model user? This changes reproducibility and cost.
- Which obligations have exact observable evidence, and which need human-calibrated semantic grading?
- What per-run spend and latency limits make a deliberate paid comparison useful?
- Does the owner need generalization beyond the authored scenario pack? If so, which scenarios remain held out from strategy development?
- What repeat-variation range changes a decision enough to justify extra model calls?
